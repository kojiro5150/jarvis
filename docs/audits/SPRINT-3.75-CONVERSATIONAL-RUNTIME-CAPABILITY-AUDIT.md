## 1. Executive Summary

**Finding — Observed in current source.** The visible DAWNWATCH specialist input uses the general
`POST /api/chat` ordinary-conversation branch. `DashboardShell` resolves the selected agent and owns
`useAgentConversation`; `ConversationDock.handleSubmit` passes text to the hook; the hook sends
`{ agentId: "dawnwatch", messages }` with no `capability`; the route resolves DAWNWATCH, builds legacy
`OperationalState`, serialises its `"full"` scope into text, assembles the agent/BOA/context system
prompt, calls Claude through `executeAuditedChat`, and returns the unmodified text for Markdown
rendering. No DAWNWATCH-specific conversational API participates.

The default conversational path does **not** consume `ExecutiveStateSnapshot`, `ExecutiveContext`,
or direct Gmail content retrieval. It does consume `OperationalState.gmailThreads`. Although the
same state contains governed `gmailRecipientEvidence`, `buildContextBlock` never reads it. The model
receives each selected legacy message's subject, sender, snippet, unread marker (when true), and
non-main source label, plus a heuristic “requiring attention” count and heuristic ordering. It does
not receive message ID, received time, recipients, explicit `needsReply`/`important` values, governed
evidence status/provenance, full body, or attachments through ordinary chat.

The response is generated by the configured Claude model. Neither “Subject / Assessment /
Recommendation” nor those exact headings occur in the DAWNWATCH prompt, the framework BOA output,
or a response formatter. On available evidence they are model-created wording, influenced by broad
instructions to rank, explain relevance, advise, and distinguish recommendation. There is no
response schema or factual/semantic claim validator. Audit persistence is fail-closed before a
successful reply is returned, but it records execution metadata—not the prompt, reply, evidence
references, or claim sufficiency. Ordinary chat is therefore operationally audited but its claims
are not governed.

**Central risk — Inferred from multiple repository facts.** The prompt declares fallback-capable
legacy state “authoritative,” orders the model not to question accuracy or say information is
unavailable, and omits connector status and governed coverage. Consequently a local/mock or fallback
record can be answered from without mandatory limitation disclosure. Phase III remains correctly
classified by the Roadmap as not started and highest value.

### Most plausible production trace

**Inferred from multiple repository facts.** With DAWNWATCH active, the input submits ordinary chat,
not a capability request. The request shape is approximately:

```json
{
  "agentId": "dawnwatch",
  "messages": [{ "role": "user", "content": "what's Cassie's email? anything important?" }]
}
```

The actual request also contains earlier in-memory turns if the session had them. The route rebuilds
state at request time. A matching legacy Gmail record, if among the five selected messages, would be
represented only as:

```text
<subject> (from <from>[, unread][, <non-main source label>]) — <snippet>
```

Thus the model could have had Cassie's email address **only if it appeared in the `from` string,
subject, snippet, or prior conversation history**. Ordinary context supplies no recipient header or
governed recipient evidence. The decisive information cannot be assigned to subject versus snippet
without the captured state/prompt. Likewise, “important” may have been model interpretation of
subject/snippet, unread/source-label/count/ranking cues, prior history, or unsupported inference;
the runtime does not capture claim lineage.

The exact `Subject / Assessment / Recommendation` wording is not required by any inspected prompt or
formatter. It is therefore best classified as model-created framing, plausibly encouraged by
DAWNWATCH's relevance/ranking/advisory instructions, but its precise causal explanation is
unrecoverable. No coverage limitation is forced into ordinary replies. Without the record and exact
reply, this audit cannot determine whether the live answer was adequately supported.

This analysis does **not** reproduce the live output and does not construct a fixture. A future
deterministic fixture could demonstrate serialization, but it would not prove what the live model
received or said.

## 5. Client Request Path

1. `DashboardShell` initially selects `jarvis`; the operator selects DAWNWATCH through `AgentRail`,
   which calls `setSelectedId`. `getAgent(selectedId)` resolves the active definition.
2. `DashboardShell` calls `useAgentConversation(agent)`. Changing `agent.id` clears in-memory
   messages/errors/loading; no cross-agent history is retained.
3. `ConversationDock` receives the active agent, messages, and `onSend={send}`. DAWNWATCH has no
   special placeholder entry, so the fallback displays `Ask DAWNWATCH anything...`.
4. `ConversationDock.handleSubmit` prevents default submission, rejects blank/loading input, calls
   `onSend(input)`, and clears the input. No capability detection, retrieval, specialist handoff, or
   DAWNWATCH-specific client branch occurs.
5. `useAgentConversation.send` trims text, appends a user `ChatMessage`, and posts JSON to
   `/api/chat`: `{ agentId: agent.id, messages: nextMessages }`. The hook never supplies `capability`.
6. On a successful response, it reads `data.reply` without inspecting returned `agentId`, appends it
   as an assistant `ChatMessage`, and retains the full history in React state. Network/server errors
   become an error string; there is no structured unavailable/unsupported state.
7. `ConversationDock` renders user text directly. Assistant text passes through `AgentDocument` to
   `MarkdownMessage`; DAWNWATCH receives static “DAWNWATCH REPORT” chrome and a render-time clock.
   `MarkdownMessage` uses ReactMarkdown/GFM/highlighting and, for two or more `##` headings, creates
   collapsible sections. It does not create `Subject`, `Assessment`, or `Recommendation` text.

The governed DAWNWATCH opening presentation is independently built before the message list. Its
voice is rendered in the same dock, but it is neither sent by the hook nor injected by the server as
conversation history. Visual adjacency does not make opening presentation evidence conversational
input.

## 6. Server Request Path

`POST /api/chat` parses JSON into optional `agentId`, `messages`, and `capability`.

### Ordinary branch used by the visible input

1. Because `capability` is absent, capability parsing/routing is skipped.
2. `isValidMessages` accepts only nonempty user/assistant strings shorter than 8,000 characters;
   the route rejects empty history and more than 40 turns.
3. `getAgent(agentId ?? "jarvis")` resolves the agent. Registry lookup is deterministic; invalid IDs
   resolve according to registry behaviour rather than a client handoff.
4. `buildOperationalState()` concurrently reads memory and Calendar/Gmail/Drive connectors.
5. `buildContextBlock(state, agent.contextScope)` serialises legacy state. DAWNWATCH's scope is
   `"full"`.
6. `assembleAgentSystemPrompt(agent, getBoaInstruction(agent.id), contextBlock)` concatenates agent
   prompt, generated framework BOA prompt, and context in that order.
7. `executeAuditedChat` verifies declared `advise` authority, calls `callClaude`, appends an execution
   record, and only then returns model text.
8. The route responds `{ reply, agentId: agent.id }`. It performs no response transformation.

Invalid input fails closed with 400. State/model/audit failures fail closed with 502 and bounded UI
copy. Successful semantic claims fail open: there is no evidence/claim gate after generation.

### Alternate routes and selectors

- A **separate branch in the same endpoint** runs only when `body.capability !== undefined`; it does
  not resolve an agent, build `OperationalState`, assemble a prompt, call Claude, or append the
  ordinary execution audit.
- No ordinary-language intent classifier promotes a question to capability routing.
- No DAWNWATCH-specific conversational route participates. `/api/dawnwatch/evaluation` is an
  isolated presentation-evaluation endpoint, not the conversation path.
- The DAWNWATCH presentation selector affects only the opening presentation. Dashboard presentation
  selectors and specialist switching do not alter `/api/chat` routing.
- No automatic agent handoff or server-side specialist router occurs in the ordinary branch.

## 7. Agent and Prompt Assembly

DAWNWATCH is an executive-tier agent with `contextScope: "full"` and declared `advise` authority.
Its behavioural contract asks it to rank current priorities, projects, signals, and schedule by
urgency/consequence/timing, explain why items matter, use supplied state, distinguish fact from
inferred significance, and escalate inconsistent/insufficient state.

The effective system prompt is a plain concatenation of:

1. **Agent system prompt.** Says the operational block is “the read,” instructs DAWNWATCH to turn it
   into a ranked current view, never claim lack of data, and use concise briefing voice. The explicit
   top-3–5/urgent output applies “when asked for a briefing,” not every answer.
2. **BOA framework instruction.** DAWNWATCH has no specialist-authored BOA content; the registry
   generates version `0.1.0`, status `framework`, containing shared instructions to distinguish
   evidence/inference/assumption/recommendation, surface material uncertainty, remain advisory,
   escalate for human assessment, and return the requested specialist artefact.
3. **Legacy context block.** Labels application state authoritative, directs the model to reason from
   it, not question accuracy/source, and not claim it unavailable. It then includes a UTC relative
   date reference, baseline, active projects, blockers, and communications.
4. **Conversation messages.** `callClaude` passes every user/assistant turn supplied by the client in
   order, separately from the system prompt.

There is tension rather than an enforced resolution between prompts: shared BOA says disclose
uncertainty and DAWNWATCH says escalate insufficient state, while the context header says not to
question accuracy/source or claim unavailability. No deterministic mechanism adjudicates that
tension.

No prompt text requires the exact headings `Subject`, `Assessment`, or `Recommendation`. No agent
metadata formatter produces them. Broad “advise,” “why it matters,” “inferred significance,” and
recommendation-distinction language permits such framing, but does not prove why the sampled model
chose it.

## 10. Legacy Heuristic Inventory

`normalizeGmailMessage` maps `UNREAD` to `unread`, sets `needsReply = unread`, maps Gmail
`IMPORTANT`, and attaches source label from query membership. Local normalization synthesises
unread and needs-reply as true, important as false, source `local`, and approximate receipt time.

`sortAndPrioritizeEmails` adds 3 for unread; 2 for board/governance keyword in subject/snippet; 2
for Governance Engineering source attribution; 1 for Gmail important; and 1 for needs-reply, then
breaks ties by receipt time. Since unread and needs-reply coincide, unread effectively contributes
four points. Google fetches up to twice the requested limit, ranks, then retains five for
`OperationalState`; local data is sliced before normalization and receives no equivalent cross-set
ranking.

`urgentCommunications` (shared by opening briefing/context) selects `unread || needsReply ||
important`; context labels its length “requiring attention.” These are deterministic computations,
but their inputs and semantics are legacy/provider/heuristic—not constitutionally authorised
attention findings.

## 11. Governed Evidence Usage

`loadGmail` produces legacy messages and governed recipient evidence from one Google acquisition.
The governed value carries normalized observations, source ID, availability, detailed state,
observation time, and snapshot ID; failure/local cases carry explicit unavailable states.

**Observed in current source:** ordinary conversational prompt construction reads only
`state.gmailThreads`. There is no reference to `gmailRecipientEvidence`, `gmailStatus`, recipient
headers, snapshot ID, or observation time in `context-builder.ts`. Therefore governed evidence is
present in `OperationalState` but omitted from DAWNWATCH conversation, both directly and
indirectly. Its coexistence in the state object does not govern the legacy prompt.

## 12. Model Input and Synthesis

`callClaude` invokes the configured Anthropic model with a scalar system prompt, configured maximum
tokens, and mapped conversation messages. It returns the first text block or an empty string. There
is no tool call, retrieval augmentation, response schema, structured-output parser, retry, citation
injection, or model-output transformation in this path.

For a selected communication the model receives subject, sender, snippet, conditional unread flag,
conditional non-main source label, the overall attention count, and positional ordering. It does not
receive explicit important/needsReply values (although they influence count/order), IDs, receipt
time, recipients, body, attachments, Gmail availability, or provenance.

Facts in the string are supplied evidence only to the extent their upstream legacy source supports
them. Any identity resolution, “important” judgment, assessment, or recommendation is model
interpretation/wording unless already literally present in subject/snippet/history. Fluent output is
not evidence of correctness.

process/infrastructure. They do not fail closed on unsupported facts or inadequate evidence.

## 14. Response Validation Analysis

There is no response validator in ordinary chat. A successful model string—including empty string—is
accepted, audited, returned as `reply`, stored client-side, and rendered. No code checks factual
claims, evidence references, uncertainty, prohibited significance, recommendation language,
Markdown safety beyond renderer defaults, output contract, or consistency with state.

The only pre-model semantic gate is that the selected agent declares `advise`. It constrains declared
authority but not the content of the advice. The capability retrieval adapter has deterministic
policy/field/outcome validation, but its returned result is separate and never post-processed into an
ordinary model answer.

## 15. Execution-Audit Analysis

`executeAuditedChat` creates one record with UUID, timestamp, selected agent, fixed step 1,
requested/granted `advise`, latest user task, message-count and injected-context constraints,
expected output, `humanApproved: false`, preparation status, execution status, and optional failure
reason. For ordinary chat it does **not** record the model name/tokens, system prompt, full history,
reply, state snapshot, evidence IDs, sources, claims, or citations.

On success the model is called first; audit append must then succeed before the reply returns. If
the model fails, a failed record is attempted and the original error is rethrown; if that append also
fails, an audit-record error replaces it. Thus persistence is fail-closed for returning a successful
reply. It proves that an advisory model execution was recorded—not that its claims were supported,
that instructions were followed, or that a recommendation was authorised by canonical evidence.

## 16. Direct Content-Retrieval Boundary

The route checks only the structural presence of `body.capability`. For explicit
`governed_gmail_retrieval`, parsing requires one identified email resource, an allowed requested-field
vocabulary, and a requesting runtime. The router constructs the Gmail adapter; policy is evaluated
before the connector; only `external_processing_permitted` can retrieve. Missing/invalid/unmatched or
non-external decisions deny without connector access. Allowed output is intersected to subject,
snippet, plain-text body, attachment filenames, and attachment MIME metadata; significance fields
are prohibited. The Google connector fetches that identified message in full. It has no search/list
method.

Ordinary DAWNWATCH UI sends no `capability`; natural language cannot trigger the branch automatically.
The Cassie exchange therefore used metadata/snippet context (and history) rather than direct content
retrieval, assuming it followed the visible input evidenced here. A future contract must separately
govern discovery/identity selection, explicit identified-resource retrieval, admissible content, and
whether/how a permitted result enters model context. Current explicit capability output is returned
to its caller as `{ capability: ... }`; it is not fused into chat.

## 17. Constitutional Responsibility Analysis

The OperationalCommunication responsibility statement permits canonical ownership of identity,
participants, sent time, threading references, and provenance. It explicitly excludes priority,
urgency, importance, labels/categories, read state, workflow/tasks/commitments, interpretation, and
executive significance.

Current conversation nevertheless exposes unread directly; uses Gmail important and needsReply in
selection/count/order; derives a Governance Engineering source label from query membership; applies
board/governance keyword scoring; and states “requiring attention.” These are facts about legacy
runtime behaviour, not authorisation by canonical communication responsibility.

The model is invited to rank by urgency/consequence/timing and explain significance. Recommendation
language is model-owned advisory wording in this runtime, not a canonical communication claim and
not execution authority. Whether a future conversation may interpret governed facts, under what
structured record and disclosure, is unresolved and requires governance. This audit does not reopen
the settled exclusions.

## 21. Non-Authoritative Governed Contract Proposal

### NON-AUTHORITATIVE — GOVERNANCE REVIEW REQUIRED

A future review—not this audit—must decide:

1. **Input authority:** whether conversation consumes `ExecutiveStateSnapshot`, deterministic
   descriptive `ExecutiveContext`, another governed projection, or a narrow view; and whether
   `OperationalState`/`gmailThreads` are excluded or retained only as non-authoritative adapters.
2. **Communication evidence:** permitted identity, sender, recipient, subject, snippet, sent-time,
   references, provenance, observation time, and content fields; explicit exclusion of read state,
   Gmail importance, needs-reply, labels, heuristic ranking, and significance unless independently
   governed.
3. **Sufficiency:** deterministic meanings and rendering for available, insufficient coverage,
   unavailable, unsupported, stale, and possibly conflicting evidence; rules for negative claims,
   person/contact lookup, temporal questions, partial selection, and source failure.
4. **Retrieval:** keep ordinary context separate from explicit, identified-resource, policy-gated
   content retrieval; determine who may select identity, which fields may reach an external model,
   and how denial/failure becomes conversation state.
5. **Model boundary:** structured facts/status/provenance first; model interpretation and natural
   language second. Decide whether assessment/recommendation are permitted, how they are labelled,
   what reasoning/evidence record precedes them, and how operator authority remains final.
6. **Validation/audit:** response schema, factual claim/evidence references, unsupported-claim gate,
   required uncertainty, citation rendering, history provenance, and an audit record joining request,
   snapshot/context version, retrieval decision, structured reasoning, model execution, validator
   result, and returned voice without treating logging as correctness.
7. **Migration:** use the established sequence—govern, implement in parallel, deterministic fixtures
   plus authenticated evaluation, explicit selector, integration, operator verification, promotion,
   and retirement of parallel authority. No selector or cut-over is authorised here.
